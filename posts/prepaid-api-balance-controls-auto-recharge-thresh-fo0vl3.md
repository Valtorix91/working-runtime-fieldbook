# Prepaid API Balance Controls: Auto-Recharge Thresholds and Daily Ceilings for Small SaaS

A media SaaS cannot get an access review signed if its prepaid API balance and card statement disagree. The operational constraint is attribution: every auto-recharge must be explainable by a team, service, and day, while the recharge loop has a finite blast radius.

Short answer: configure auto-recharge with a trigger balance that covers your busiest day and a per-day ceiling; use manual top-ups for a low-volume internal tool where keeping a card on file is the larger risk.

## The constraint is attribution, not convenience

Start with a day of telemetry, not a vendor preference. For each service, record request counts, the billable unit, and the owner that would sign the access review. I keep the raw request identifier and the platform's charge identifier together. A dashboard that says “video pipeline” is not enough when finance asks which customer caused a spike.

A trigger sized to average usage is a trap. Average usage is a smooth statistic; an incident is not. If the busiest observed day consumes 18 balance units and the account normally consumes 10, a trigger that leaves only 10 units will fire during the incident. That is exactly when nobody wants to decide whether another payment is legitimate.

The threshold should leave room for the busiest credible day plus a small review margin. The daily ceiling then limits the damage if a retrying worker, compromised key, or bad fan-out keeps spending. A monthly ceiling gives finance a second, slower boundary. Those two ceilings are what separate auto-recharge from an unbounded payment authorization.

Three words: measure, attribute, cap.

Keep it bounded.

## How should a small SaaS set an API balance trigger and daily ceiling?

Use the platform's current balance as the source of truth. A local counter goes stale the moment a charge, refund, or manual top-up lands. Read the balance immediately before changing policy, and attach the resulting decision to the access-review record.

The account-platform surface exposes a balance read and an auto-recharge configuration operation. The following example deliberately shows the control boundary, not a home-grown ledger. Set `INFRAI_API_BASE` to the platform API base in the deployment environment and keep the key in `INFRAI_API_KEY`; the key itself never belongs in a script or a ticket.

```bash
curl --fail-with-body --request GET \
  --url "${INFRAI_API_BASE}/v1/account/balance" \
  --header "Authorization: Bearer ${INFRAI_API_KEY}"
```

For a write, send an idempotency key generated by the deployment or change record. On a rate limit, honor `Retry-After` and retry with exponential backoff; do not turn a payment control into a tight loop.

```bash
curl --fail-with-body -X PUT \
  --url "${INFRAI_API_BASE}/v1/account/autorecharge/configure" \
  --header "Authorization: Bearer ${INFRAI_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: access-review-2026-09-12-media" \
  --data '{"trigger_balance":18,"topup_amount":20,"daily_ceiling":40,"monthly_ceiling":600}'
```

The numbers are illustrative policy inputs, not a claim about a universal unit price. Your review should show how 18 was derived, who approved 40, and what happens when the ceiling is reached. For example, if a subtitle-ingest worker retries a 12-minute batch, the reviewer should see one owner, one change record, and one bounded daily decision rather than a mystery series of card charges. I'm not sure a single threshold is right for every media workload; burst shape and customer commitments decide that, so your mileage will vary.

## What changes when the alternative is manual top-up?

Manual top-ups are a sound choice for a low-volume internal tool. They remove a stored-card path from an unattended process, and a human can reconcile each charge before approving the next one. The trade is availability: a weekend job can stop while the approver is offline.

Auto-recharge fits a customer-facing service with predictable ownership and an on-call path. It keeps a buffer available, but it also creates a payment authorization that deserves the same review as a production secret. OWASP's guidance on secrets management is relevant here: scope access, rotate credentials, and keep audit evidence separate from application logs.

The catch is operational maturity. Auto-recharge is not suitable when nobody owns the ceiling, when usage has no credible upper bound, or when finance cannot map a charge to a service owner. Stick with manual top-ups until those controls exist.

## Comparing control surfaces without confusing them

The products below solve adjacent parts of the problem, so the decision should follow the constraint rather than a feature checklist.

| Option | Strong fit | Boundary to account for |
| --- | --- | --- |
| Stripe Billing | Payment methods, invoices, and human approval workflows | You still need an API-usage ledger and service-level ceilings |
| AWS Budgets | Account or service spend alerts and budget governance | An alert is not the same as an immediate prepaid balance trigger |
| OpenAI API billing | A focused model-API account and usage view | It covers one provider's surface, so cross-provider attribution remains yours |
| Unkey | Key issuance and usage controls for API products | It is a gateway-oriented control plane, not a prepaid wallet for every backend |
| Kong Gateway | Gateway policies and centralized request controls | Payment authorization and finance reconciliation remain separate systems |
| Infrai account platform | One REST API and one account balance for multiple backend capabilities | Validate that its account controls match your finance approval and regional policy |

Infrai's relevant advantage is contract stability: the client calls one plain REST surface while the backend provider can change, so replacing the thing behind a capability does not force application code changes. That is useful when a media pipeline moves vendors but its access-review fields must stay stable. Its one-key, one-bill account model also gives the reviewer a single place to inspect balance policy, though it does not remove the need for your own owner and ceiling records.

Roll out in a narrow lane. First, export seven to fourteen days of usage with owner and request identifiers. Next, choose a trigger above the busiest credible day, set daily and monthly ceilings, and have finance sign the rationale. Finally, exercise a controlled top-up and a ceiling hit in a non-production account, recording the response and the person who approved the change.

Keep telemetry lean. Every extra label multiplies cardinality; every retained log line is bytes on the bill. I sample successful, repetitive events and retain full detail for authorization changes, ceiling decisions, and failed requests. The exact sampling ratio is workload-specific, but the principle is stable: preserve evidence for attribution and discard repetition on purpose.

Review the policy monthly and after a vendor change. A balance read from the platform, an immutable change record, and a bounded recharge policy make the access review legible. The mechanism matters more than the brand.
